# HR-Avatar

> **Placeholder name.** "HR-Avatar" lives only in `service/config/hr-avatar.php`, the SDK
> `package.json` name, the key prefix constants (`hra_sk_`, `hra_pk_`) and the `HRA_` env
> prefix. Renaming the product is a find-and-replace, never a redesign.

Standalone, provider-agnostic **avatar conversation engine**: it creates, drives and tears down
real-time avatar conversations (Tavus, HeyGen LiveAvatar) for any host product. It has **no back
office and no UI** — only an HTTP API (`service/`) and a browser SDK (`sdk/`).

It was extracted from BEAI (an HR assessment platform). The approved analysis and design live in
the BEAI wrapper: `docs/extraction/FINDINGS.md` and `docs/extraction/DESIGN.md`.

## Binding rules (also the Guardian Angel review rules)

### Boundary
- **No host-product concepts.** No participant, candidate, competency, BARS, interview, project,
  organization, assessment, score or tenant-of-BEAI vocabulary in code, schema, API or docs. A host
  passes an opaque `external_ref` and free-form `metadata`; HR-Avatar never interprets them.
- **Account is the only tenant key.** Every table except platform catalogues carries
  `account_id`; every query is scoped by it. Cross-account reads are a security defect.
- **Provider-agnostic core.** Provider specifics live only in adapter classes behind the provider
  contract. Nothing outside an adapter may branch on a provider name.

### Security
- Secret keys (`hra_sk_{live|test}_…`) are server-to-server only: stored as sha256 hash +
  indexed prefix, compared with `hash_equals`, never logged, never returned after creation. A
  live secret key presented with an `Origin` header is rejected.
- Publishable keys (`hra_pk_{live|test}_…`) are browser-safe, origin-allowlisted, and grant
  nothing on their own; browser calls also require the per-conversation `client_secret` JWT.
- Provider and LLM credentials are encrypted at rest (Eloquent `encrypted` cast), hidden from
  serialization, and never returned by any endpoint (last four characters at most).
- Inbound provider webhooks are authenticated (per-conversation unguessable token, plus the
  provider signature when the provider offers one) and idempotent.
- Outbound webhooks are HMAC-signed: `X-HRA-Signature: v1=<hex hmac_sha256("{ts}.{body}")>`.
- Validate every input at the HTTP boundary (Form Requests); no mass assignment of `account_id`.

### API
- API-only, versioned under `/v1`. Errors are RFC 9457 Problem+JSON with a stable `code`.
- OpenAPI is generated by **Scramble** and committed; a CI step fails on drift.
- Machine-facing values (enums, field names, error codes) are never localized.

### Engineering
- **Strict TDD**: a failing test precedes every unit of behavior. Never weaken an assertion,
  skip a test or lower a coverage threshold to get green.
- Coverage: service `--min=90`; auth/keys, webhook signatures and the conversation state machine
  held to ~95%. SDK Vitest thresholds 90.
- SDD: every change goes through `openspec/` (proposal → spec → design → tasks → apply).
- Package manager for `sdk/` is **Bun** only (never npm/pnpm/yarn/npx).
- English only: code, identifiers, comments, docs, commit messages.
- Conventional commits. Git Flow: `main` / `develop` / `feature/*`. **No deploy**: Railway
  config exists as code only and is never applied from this repo.
- Keep it boring: no interface with one implementation unless it is the provider contract, no
  speculative configuration, smallest diff that is correct.
